El CORE nativo de Portal APM

Portal APM no tiene lógica de negocio propia — es un hub: login, sesión, permisos por rol, menú, y el framework mínimo que hace correr los controladores de modules/Central/, más la infraestructura compartida que usan TODAS las apps del sistema (portal + TH + Bienes + Bitácoras). Esta guía es interactiva: buscá, filtrá por estado (real/muerto/gotcha) y navegá el árbol real del proyecto.

§1 Ciclo de vida de un request

Desde que Apache/IIS recibe la URL hasta que index.php termina de armar la respuesta.

1a

Antes de index.php: enrutamiento de servidor

Dos archivos de configuración, uno por plataforma, con una discrepancia real entre ellos:

🟢 .htaccess (Apache / XAMPP / Wamp)

Si la URL no es directorio ni archivo real, reescribe TODO a index.php sin query string. index.php lee REQUEST_URI directo — calza perfecto.

gotcha web.config (IIS)

Reescribe a index.php?url={R:1} con parámetro url. Pero index.php nunca lee $_GET['url'] — no rompe nada (usa REQUEST_URI igual) pero es evidencia de que web.config quedó desactualizado. No hay despliegue IIS verificado en este proyecto.

1b

index.php — orden exacto de ejecución

portal_apm/index.php

No hay contenedor de dependencias, no hay middleware pipeline. Cada Controller resuelve sus propias dependencias llamando a Database::getInstance() — deliberadamente simple.

1

Polyfills primero

helpers/polyfills_php74.php — antes que nada, porque el resto usa str_starts_with()/str_contains()/str_ends_with() sin guardas.

2

Modo php -S

Si la URL pedida es un archivo real en disco, return false y el servidor lo sirve tal cual (assets, legacy). En Apache lo hace .htaccess; este bloque replica el comportamiento para pruebas sin XAMPP.

3

Bootstrap de configuración

core/Env.php se carga pero no se usa (§7) → config/app.php define ROOT, APP_URL, DEFAULT_TIMEZONE, SESSION_TIMEOUT, y lee connections.php para espejar DB_*.

4

error_reporting

Según DEBUG_MODE (constante en app.php, true en desarrollo).

5

Sesión PHP

session.gc_maxlifetime = SESSION_TIMEOUT, session.cookie_lifetime = 0 (cookie de sesión, no persistente), session_start().

6

Autoload de las 9 clases core

Vía require_once explícito — sin autoloader, a propósito: son pocas clases, más simple que un autoloader para 9 archivos.

7

Autoloader real

spl_autoload_register — solo para clases de módulos: busca en modules/*/controllers, modules/*/models, y los directorios legacy. Primera coincidencia gana.

8

Helpers cargados siempre

5 archivos listados a mano, sin autoload. libs/* (§6b) NO se carga acá — cada controlador hace su propio require puntual.

9

Rutas + dispatch

new Router(), require routes.php, $router->resolve($uri, $method) dentro de un try/catch (Throwable) — 500 genérico en producción, stack trace completo en DEBUG_MODE.

10

Normalización de URI

Antes de resolve(), se quita el subdirectorio del script (dirname($_SERVER['SCRIPT_NAME'])) — así /portal_apm/dashboard y /dashboard resuelven igual sin importar raíz de dominio o subcarpeta.

§2 Router — mapeo de URLs

core/Router.php, 62 líneas.

PHP
$router->get('/dashboard', 'DashboardController@index');
$router->post('/login',    'AuthController@login');
  • Match exacto primero. Si no hay, recorre rutas con {param} y las convierte a regex ({id} → ([^/]+)) — sin caché de compilación, se recompila cada request (irrelevante: ~100 rutas).
  • Cast automático de parámetros numéricos: un {id} que matchea solo dígitos se castea a int antes de pasarlo — un controlador declara ver(int $id) sin (int) manual.
  • dispatch() instancia el controlador (new $class(), sin inyección de nada) y llama al método con ...$castParams (spread).
  • 404: si nada matchea, JSON {"error":"Not found"} para AJAX (header X-Requested-With) o 404.php para el resto.
No hay grupos de rutas, prefijos, ni "middleware" declarativo — el control de acceso vive dentro de cada controlador, llamando a $this->requireAuth() / requireLevel() como primera línea (§3).

§3 Controller — la clase base real

core/Controller.php, abstracta, 195 líneas. Todo controlador de modules/Central/controllers/ extiende de acá.

◆

Constructor

PHP
public function __construct() {
    if (session_status() === PHP_SESSION_NONE) session_start();
    SecurityHelper::setSecurityHeaders();
}

Se ejecuta en cada instanciación. session_start() es defensivo (ya se llamó en index.php, pero un controlador podría instanciarse fuera del flujo normal en tests) y los headers de seguridad se fijan siempre, autenticado o no.

◆

requireAuth(?string $module = null)

parámetro vestigial

Guard de autenticación básico. Si no hay $_SESSION['user_id'], redirige a /login (o 401 JSON si es AJAX). El parámetro $module está declarado pero no se usa dentro del método — vestigial de un diseño anterior; el control por módulo real pasa por requireLevel().

Timeout de inactividad real — no es un valor fijo. Llama a resolveInactividad():

1. Caché de sesión
< 5 min → lo usa, evita golpear la BD
→
2. SQL Server
fn_InactividadSegundos / fn_InactividadAvisoSegundos — cascada usuario → módulo → global
→
3. Fallback
BD no responde → 1800s/60s por defecto, nunca deja sin timeout

Mismas funciones SQL que usan TH, Bienes y Bitácoras — mecanismo real detrás del "sistema de inactividad centralizado". Front-end: js/inactivity-warning.js (§8b). Si venció, destruye la sesión y redirige con ?timeout=1; si no, actualiza last_activity en cada request — timeout deslizante, no absoluto.

◆

requireLevel(int $minLevel, ?array $nodo = null)

el control de acceso real
PHP
protected function requireLevel(int $minLevel, ?array $nodo = null): void {
    $this->requireAuth();
    if (($_SESSION['nivel_jerarquia'] ?? 0) < $minLevel) $this->denyAccess();
    if ($nodo !== null && !$this->tienePermisoNodo(...$nodo)) $this->denyAccess();
}

Dos capas de control, ambas opcionales de combinar:

1. Nivel de jerarquía

$_SESSION['nivel_jerarquia'], entero 1-4, poblado en login desde CORE_Usuarios. Check "grueso": ¿AL MENOS este nivel? No distingue módulo ni pantalla.

2. Nodo MOIS granular (opcional)

Tupla [id_modulo, opcion, items, subitems, nivel_crud_minimo] contra fn_TienePermisoNodo(...). CRUD: 1=Ver, 2=Crear, 3=Editar, 4=Total.

Ej.: requireLevel(2, [11, 3, 0, 0, 2]) exige nivel ≥2 y permiso "Crear" sobre el nodo (módulo TH, opción 3) configurado en /admin/roles/{id}/permisos. Sin $nodo, comportamiento histórico (solo nivel) — así queda explícito qué pantallas migraron a permisos granulares.

◆

CSRF, JSON, redirect, sanitización

  • csrfToken()/verifyCsrf() delegan 100% a SecurityHelper (§8) — el Controller no reimplementa nada.
  • json($data, $status=200): siempre exit después de imprimir — nunca sigue ejecutando código del controlador.
  • redirect($path): si no empieza con http(s)://, lo ancla a APP_URL — funciona igual en raíz de dominio o en /portal_apm.
  • input($key, $source='both', $default=null): lee de $_POST/$_GET/ambos, trim() automático. No sanitiza contra XSS — para eso sanitize() aparte.
  • currentUser(): array plano desde $_SESSION — forma estándar de leer "quién es el usuario actual".

§4 Database — singleton sqlsrv, sin PDO

core/Database.php, 109 líneas.

Decisión de arquitectura explícita en el comentario de cabecera: NO PDO, exclusivamente el driver nativo sqlsrv_*.

  • Singleton real (self::$instance, constructor private) — una sola conexión por request, reutilizada por todos los Model.
  • Configura sqlsrv_configure("WarningsReturnAsErrors", 0) antes de conectar gotcha — sin esto, un PRINT o warning SQLSTATE 01 dentro de un SP hace que sqlsrv_query() devuelva false como si hubiera fallado de verdad.
  • query($sql, $params=[]): sin parámetros usa sqlsrv_query() directo; con parámetros, sqlsrv_prepare() + sqlsrv_execute(). Cada valor se normaliza — array (OUTPUT/INOUT) se respeta tal cual, valor simple se envuelve como [$valor, SQLSRV_PARAM_IN].
  • fetch()/fetchAll() devuelven arrays asociativos, nunca objetos.
  • lastInsertId() usa SELECT SCOPE_IDENTITY() en query aparte gotcha — puede devolver NULL si INSERT y SELECT no van en el mismo scope. Alternativa usada en el resto del proyecto: OUTPUT INSERTED.id directo en el INSERT.
  • beginTransaction()/commit()/rollback(): pasamanos directos a sqlsrv_begin_transaction/commit/rollback, sin anidamiento ni savepoints.
  • Database::reset() existe solo para tests — nada del flujo normal lo llama.
Conexión a otras bases (Talento_Humano, inventario, PortuariaDemo…) no pasa por esta clase — cada lugar abre su propio sqlsrv_connect() ad-hoc leyendo connections.php directo (SyncPermisosModulo §10, SsoClient §6b, NotificacionGeneradorModel). Database es exclusivamente PORTAL_APM.

§5 Model y View — minimalismo deliberado

📦 Model (55 líneas)

Abstracta, puro thin wrapper sobre Database::getInstance(): query(), fetch(), fetchAll(), rowsAffected(), lastInsertId(), transacciones, y outParam() (arma el array para parámetros OUTPUT de un SP).

No hay ORM, no hay mapeo de columnas a propiedades, no hay validación — cada modelo escribe su SQL a mano.

🖼️ View (66 líneas)

  • render($view, $data, $useLayout=true): extract($data, EXTR_SKIP), decide si envolver en el shell. AJAX nunca recibe el shell (mismo header X-Requested-With).
  • Resolución: "Central/dashboard/index" → modules/Central/views/dashboard/index.php, con fallback legacy.
  • partial() = azúcar para render(..., useLayout: false).

§6 ModuleSecurity — 3 responsabilidades, 3 destinos distintos

core/ModuleSecurity.php, 193 líneas. La sección más importante para entender qué es "real" en este proyecto.

⚫

generateSSOToken() / verifySSOToken()

código muerto

SSO token JWT-like casero — payload {id, cedula, ip, exp} en base64url + firma HMAC-SHA256 (base64.firma, no JWT estándar). Expira a los 1800s. Atado a IP (excepción 127.0.0.1 para desarrollo). Secreto (SSO_SECRET) desde CORE_Config, con fallback hardcodeado solo si la BD no responde.

Búsqueda directa en todo el repo: ningún archivo fuera de ModuleSecurity.php llama a estos dos métodos. El SSO real y activo es libs/SsoClient.php (§6b). Candidato a eliminar si se confirma que nada externo lo invoca tampoco.

⚫

checkAccess()

código muerto

Mismo mecanismo que Controller::requireLevel() con $nodo (§3), pero como método estático standalone — pensado para código que no es un controlador. Trae su propio mapa $moduleCode → id_modulo ('TH'→11, 'BIENES'→9, 'ACCESO'→5…) gotcha duplicado respecto al que usa CatalogoModulos/CORE_Modulos.

Búsqueda directa confirma cero callers en todo el repo — el control de acceso real siempre pasa por Controller::requireLevel(), no por acá.

🟢

audit()

este sí tiene caller real

Escribe a la tabla de auditoría central llamando a sp_RegistrarAuditoria con 11 parámetros posicionales. El código documenta un bug real ya corregido: la firma anterior no calzaba con el orden de parámetros del SP (el user-agent terminaba en la columna @resultado) — no se detectó en producción porque nada lo llamaba todavía en ese momento.

Hoy sí tiene caller real, muchos:

  • AdminController.php — 17 puntos: usuarios, roles, permisos individuales, departamentos, config.
  • ModuloController.php — alta/edición de módulos.
  • Credenciales/AuthController.php — activar/desactivar MFA.

Es la ruta de auditoría real del portal nativo, a diferencia de los dos métodos anteriores.

§6b libs/ — infraestructura PHP compartida entre TODAS las apps

A diferencia de core/ (solo el portal), libs/ lo consume cualquier módulo/app con un require puntual.

🟢

SsoClient.php

9.8 KBel SSO real y activo

Documentado en detalle en GUIA_SSO_LOGIN_ENTRE_MODULOS.md. Este es el mecanismo a usar cuando se piensa en "SSO del Portal APM" — no el de ModuleSecurity (§6, muerto).

  • Clase standalone, propia sqlsrv_connect() a PORTAL_APM (no reutiliza Database — apps externas pueden no tener el resto del framework cargado).
  • login()/validate()/logout() llaman a sp_SSO_Login/sp_SSO_ConfirmarLogin/sp_SSO_ValidarToken/sp_SSO_Logout/sp_SSO_RegistrarFallo — nunca SELECT directo a CORE_Usuarios.
  • Verificación de contraseña replicada, no reusada: verifyPassword() (privado) reimplementa el mismo esquema que SecurityHelper::verifyPassword() a propósito, porque apps externas solo tienen acceso SQL, sin el resto del código PHP cargado.
  • Superficie HTTP: ApiSsoController.php expone POST /api/sso/{login,validate,logout} — cadena completa routes.php → ApiSsoController → SsoClient → sp_SSO_* confirmada activa.

🟢 XlsxWriter.php

Construye el ZIP a mano ("stored", sin compresión, + CRC32) — sin Composer ni ZipArchive. Caller real: AdminController.php.

gotcha No confundir con apps/talento_humano/core/XlsxWriter.php — implementación DISTINTA (usa DEFLATE real vía gzdeflate()), no comparten código.

🟢 ReportPdf.php + fpdf/

tabla() (reporte con membrete, encabezado repetido, zebra) y ficha() (clave/valor por secciones), sobre fpdf vendorizada. Envían el PDF inline y hacen exit. Caller real: AdminController.php.

§8 Helpers nativos que se cargan siempre

🛡️

SecurityHelper

helpers/security_helper.php, 177 líneasel más importante

CSRF

csrfToken() genera/reutiliza $_SESSION['_csrf_token'] (32 bytes random). verifyCsrf() compara con hash_equals(); si falla, ya no muere con JSON crudo — AJAX recibe JSON con redirect, cualquier otro POST va a /login?timeout=1 (un mismatch de CSRF casi siempre es sesión vencida, no un ataque).

Peppering de contraseñas

hashPassword(): HMAC-SHA256(password, PASSWORD_PEPPER) y después password_hash(..., PASSWORD_BCRYPT), prefijo 'peppered:'. verifyPassword() acepta el esquema nuevo Y el viejo (bcrypt directo) — migración perezosa, nadie queda bloqueado. passwordNeedsRehash() avisa cuándo regrabar.

PASSWORD_PEPPER se autogenera (random_bytes(32)) y se persiste en CORE_Config — mismo mecanismo que SSO_SECRET y MFA_ENCRYPTION_KEY, nunca hardcodeado real (el fallback de SSO es la única excepción, solo si la BD está caída). El paso "SHA-256 en el navegador" lo hace js/password-hash.js (§8b) — sin ese script, el hash final sigue siendo válido pero se pierde la garantía de "la contraseña real nunca sale del navegador".

Headers de seguridad (setSecurityHeaders(), en cada Controller::__construct()): X-Frame-Options, X-Content-Type-Options, X-XSS-Protection, Referrer-Policy, y un CSP que arma frame-src dinámico para embeber el Dashboard Ejecutivo (Streamlit) de Portuaria si aplica.

getClientIp(): revisa CF-Connecting-IP → X-Forwarded-For → X-Real-IP → REMOTE_ADDR, valida con filter_var(FILTER_VALIDATE_IP).

SessionHelper (71 líneas)

Wrapper delgado sobre $_SESSION (get/set/has/remove/flash) más login(array $user) (regenera ID de sesión, cachea _requiere_mfa) y logout() (limpia sesión, borra cookie, session_destroy()).

UrlHelper (33 líneas)

base()/asset()/current()/isActive()/redirect()/back() — todo anclado a APP_URL, funcionan igual en cualquier entorno.

form_helper.php, hub_charts_helper.php, module_stats_helper.php son utilidades de más alto nivel para vistas/dashboards de Central — no documentadas función por función acá.

§8b js/ — infraestructura de cliente compartida

Contraparte de navegador de libs/ — cada app embebida la referencia vía PORTAL_ROOT_URL en vez de tener su propia copia.

🔑

password-hash.js

window.hashPasswordFieldsBeforeSubmit(form, fieldNames): SHA-256 (vía crypto.subtle) sobre cada campo, in-place, antes del submit real — la contraseña en texto plano nunca sale del navegador. Requiere contexto seguro (HTTPS/localhost); si crypto.subtle no está, la función queda undefined (fallback: se manda sin hashear, el servidor lo procesa igual pero se pierde la garantía). Campos vacíos no se tocan (necesario para "editar usuario" sin cambiar clave).

⏱️

inactivity-warning.js

el aviso centralizado real

SweetAlert2 con anillo SVG de cuenta regresiva — usado por Portal, TH, Bienes y Bitácoras por igual. Requiere window.APP_INACTIVIDAD = {timeoutSegundos, avisoSegundos, keepaliveUrl, logoutUrl} antes de cargar (TH además soporta csrfToken/logoutViaPost).

Dos bugs reales ya corregidos (documentados en el propio código):

  1. doLogout() tenía 3 caminos casi simultáneos (countdown, SweetAlert2, logoutTimer sin cancelar) → 2-3 GET /logout casi a la vez desincronizaban el _csrf_token. Fix: guardia loggedOut de una sola disparada.
  2. El keepalive cerraba sesión ante CUALQUIER fallo del fetch (incluida desconexión momentánea) → cambiado a solo cerrar cuando el servidor confirma explícitamente sesión expirada.
💬

alerts.js — window.PortalAlert

Envoltorio delgado sobre SweetAlert2 (success/warning/error, toasts en top-end) que reemplaza confirm()/alert() nativos.

Gotcha repetido en memoria del proyecto: declarar esto con const PortalAlert = ... en vez de window.PortalAlert = ... lo rompe en cualquier vista que re-ejecute sus <script> inline por navegación SPA sin reload completo — por eso el patrón window.X explícito se repite en los 3 archivos de esta sección.

main.js, datatables-init.js son utilidades de UI de más alto nivel — no documentadas función por función.

§9 config/ — una sola fuente de verdad para credenciales

config/connections.php (NO versionado en git — copiar de connections.example.php) es el archivo del que todo el sistema lee credenciales de SQL Server: el portal (vía app.php), apps/talento_humano y apps/control_bienes, libs/SsoClient.php/core/SyncPermisosModulo.php (leído directo, sin pasar por Database), y export_analytics_env.php. Archivo de datos puro (return [...], sin define()) a propósito.

Estructura real: server_default, credentials (vacío = Windows Auth), options (trust_cert, encrypt, charset), y databases (mapa nombre-lógico → nombre-real + servidor opcional) — portal, talento, portuaria, portuaria_ext, inventario.

config/app.php es el único archivo que se edita para cambiar entorno (APP_ENV, DEBUG_MODE, zona horaria, timeout de sesión).

config/export_analytics_env.php — script CLI (php config/export_analytics_env.php) que regenera analytics/.env desde connections.php, para un dashboard Python externo. Correr manualmente después de tocar connections.php.

§9b db/ — scripts de operación, NO es core de runtime

Colección de .sql sueltos (migraciones puntuales ya aplicadas: bloqueo_login_escalado.sql, mfa_portal_central.sql, notificaciones_reales.sql, permisos_centrales_fase*.sql…) más utilidades PHP CLI: run_sql.php (ejecutor universal, divide por GO), list_tables.php, alter_sp.php.

Nada de esto se carga en el bootstrap de index.php ni corre como parte de un request real — es la caja de herramientas de quien administra la base de datos, no del framework en ejecución.

§10 SyncPermisosModulo — el puente de permisos

core/SyncPermisosModulo.php, 130 líneas.

Cuando un admin cambia la matriz de permisos de un rol del portal en /admin/roles/{id}/permisos, esto replica el cambio hacia el RBAC nativo de TH y Bienes, si ese rol tiene contraparte mapeada en CORE_Roles_Modulo_Map. Caller real: AdminController.php.

Portal
/admin/roles/{id}/permisos
→
centralHaciaTh()
UPDATE th_permisos_rol · NODOS_TH (14)
→
centralHaciaBienes()
MERGE inv_permisos_rol · NODOS_BIENES (15)
  • Cada función abre su propia conexión sqlsrv al destino (lee connections.php directo, no usa Database) y traduce la opción a un codigo_modulo real vía mapa fijo.
  • Registra la sincronización vía sp_th_registrar_auditoria — auditoría en la BD destino, no en PORTAL_APM.
  • Si el rol no tiene mapeo, retorna sin hacer nada — silenciosamente, no es un error.
  • Si la conexión al destino falla, se registra el fallo vía ModuleSecurity::audit() en PORTAL_APM (porque justo ahí no se pudo conectar).
Solo cubre nodos de "opción" (items===0 && subitems===0) — la granularidad de sub-ítem del portal no tiene forma de reflejarse en el RBAC más simple de TH/Bienes. Límite consciente, no un bug.

§14 Cómo se enlazan los usuarios entre módulos, sin re-login

Esta sección faltaba en la guía original — verificada línea por línea contra el código real de las 3 apps embebidas, no asumida. Responde: ¿cómo navega alguien de TH a Bienes a Bitácoras sin volver a loguearse, y cómo se sincroniza el tiempo de inactividad entre todas?

Dos mecanismos totalmente distintos conviven, y no hay que confundirlos:

🔗 Apps embebidas (esta sección) — TH, Bienes, Bitácoras

Viven en el mismo servidor, bajo apps/*. No usan token ni contraseña de nuevo — leen la sesión PHP que el login del portal ya dejó escrita (en disco, mismo motor de sesiones), cada una a su manera. Cero llamadas HTTP, cero SQL de por medio para el puente en sí.

🌐 Apps externas — sp_SSO_*

Para lo que no comparte sesión PHP con el portal (otro servidor, app móvil, servicio en otro lenguaje). Token + procedimientos almacenados, documentado en detalle en GUIA_SSO_LOGIN_ENTRE_MODULOS.md (no repetido acá — ver §6b para el resumen).

⇄

3 apps, 3 mecanismos reales — no son el mismo patrón

Los 3 módulos son "Patrón B" (puente de sesión, no SSO por token) pero cada uno lo resuelve distinto. Verificado leyendo apps/talento_humano/index.php+core/Auth.php, apps/control_bienes/index.php+AuthController.php, y apps/bitacoras/includes/bit_auth_guard.php+modules/Portuaria/models/Auth.php:

MóduloSesión PHPCómo lee al portalLogin propioPuente inverso
Talento Humano Propia, separada — cookie APMSESSID, carpeta privada Cierra su sesión, abre la del portal solo para leerla (nombre+ruta originales), cierra, vuelve a abrir la suya con su mismo id Sí, completo (usuario/clave/MFA propios) + acepta cédula del portal para super admin Sí — syncPortalSession() escribe en la sesión del portal al loguearse nativo en TH

1

Talento Humano — el más elaborado: sesión propia + "espionaje" temporal de la del portal

index.php + core/Auth.php

TH tiene su propia identidad completa (login, MFA, bloqueo, sesión cifrada con claims AES-256-GCM en $_SESSION['auth_token']) — el puente no la reemplaza, se agrega encima. En cada request, si TH todavía no tiene sesión propia activa:

1. Cierra sesión TH
session_write_close()
→
2. Abre la del portal
nombre+ruta originales, use_strict_mode=0 — solo lectura
→
3. Lee y cierra
user_id, nivel_jerarquia
→
4. Vuelve a TH
restaura su config, mismo id de sesión TH

El paso 2 es la parte no obvia: session_save_path() es un ajuste global por request — cambiar solo el nombre de la sesión no alcanza, hay que restaurar también la ruta o TH terminaría buscando "la sesión del portal" dentro de su propia carpeta privada. Y use_strict_mode se apaga solo para este vistazo puntual: con esa bandera en 1 (como la deja Auth::configureSession() para TH), un id de sesión sin archivo real en disco haría que PHP genere uno nuevo y lo mande por Set-Cookie — exactamente lo que pisaría la cookie real del portal si alguien sin sesión ahí navega a TH primero.

PHP — apps/talento_humano/index.php
if (!Auth::check()) {
    $__thSid = session_id();
    session_write_close();
    ini_set('session.use_strict_mode', '0');
    session_save_path(PORTAL_SESSION_SAVE_PATH);
    session_name(PORTAL_SESSION_NAME);
    if (isset($_COOKIE[PORTAL_SESSION_NAME])) session_id($_COOKIE[PORTAL_SESSION_NAME]);
    session_start();
    $__portalUserId = $_SESSION['user_id'] ?? null;
    $__portalNivel   = (int)($_SESSION['nivel_jerarquia'] ?? 0);
    session_write_close();

    Auth::configureSession(); // restaura nombre+ruta+cookie propios de TH
    session_id($__thSid);
    session_start();

    if ($__portalUserId !== null) Auth::loginTrusted($__portalUserId, $__portalNivel);
}

loginTrusted() no crea una sesión "genérica" — busca la cuenta REAL de th_usuarios_sistema correspondiente: si nivel_jerarquia≥4 (super admin del portal) resuelve siempre a la cuenta fija admin_apm (no tiene empleado_id, no hay cédula que buscar); si no, hace JOIN por CORE_Usuarios.id_empleado_th = th_usuarios_sistema.empleado_id. Sin cuenta correspondiente, simplemente no hay puente — la persona ve el login propio de TH.

Puente inverso — syncPortalSession(): si alguien entra directo por el login nativo de TH (no vino del portal), TH hace la MISMA maniobra pero al revés — abre la sesión del portal (esta vez para escribir), puebla user_id, nivel_jerarquia, etc., y vuelve a la suya. Así el botón "Volver al Portal APM" funciona y del otro lado ya está autenticado, sin importar por cuál puerta entró primero.

2

Control de Bienes — sesión literalmente compartida, sin maniobra

apps/control_bienes/index.php

Bienes nunca llama session_name() ni session_save_path() — usa el nombre/ruta de sesión por defecto de PHP, igual que el portal. Resultado: es la misma sesión, no hay nada que "espiar" ni sincronizar entre archivos distintos. En cada request, si todavía no armó su propio $_SESSION['usuario'] pero ya existe $_SESSION['user_id'] (del portal), lo arma ahí mismo:

PHP — apps/control_bienes/index.php
if (empty($_SESSION['usuario']) && !empty($_SESSION['user_id'])) {
    $nivelPortal = (int)($_SESSION['nivel_jerarquia'] ?? 0);
    $rolApp = $nivelPortal >= 3 ? 'Administrador' : ($nivelPortal === 2 ? 'Supervisor' : 'Operador');
    $_SESSION['usuario'] = ['id' => $_SESSION['user_id'], 'nombre' => ..., 'rol' => $rolApp];
    // + id_usuario, usuario_id, rol a nivel raíz de $_SESSION
}

El nivel jerárquico del portal (1-4) se traduce a un rol de Bienes por umbral fijo — no hay tabla de mapeo de roles como en TH/permisos granulares (§10), es una regla simple codificada acá mismo.

Gotcha real documentado en el propio código: el control de inactividad propio de Bienes hacía $_SESSION = [] cuando veía ultimo_acceso viejo — eso borraría TAMBIÉN la sesión del portal (es la misma). Por eso, con sesión de portal activa, cada request refresca $_SESSION['ultimo_acceso']/['last_activity'] ANTES de que el chequeo de inactividad de Bienes pueda evaluarlo.
3

Bitácoras — sesión compartida + capa de traducción para código legacy

includes/bit_auth_guard.php + Portuaria/models/Auth.php

Igual que Bienes, Bitácoras comparte la sesión PHP del portal directamente — pero el código nativo de Portuaria (anterior a la integración al portal) espera sus propios datos de usuario en $_SESSION['apm_auth'] (id_usuario, nombres, cedula, nom_departa...). Auth::hydrateFromPortal() traduce uno al otro, y se re-ejecuta solo cuando detecta que el usuario del portal cambió:

PHP — modules/Portuaria/models/Auth.php
$needsHydrate = empty($_SESSION['apm_auth']['id_usuario_portal'])
    || (int)$_SESSION['apm_auth']['id_usuario_portal'] !== (int)$_SESSION['user_id']
    || empty($_SESSION['apm_auth']['id_usuario']);

bit_auth_guard.php (incluido al inicio de cada página/API del módulo) simplemente revisa si apm_auth ya quedó poblado — si no, header('Location: '.APP_URL.'/login') directo al login del portal. Bitácoras no tiene login propio: a diferencia de TH y Bienes, no hay puerta alterna — todo el que entra, entra siempre por el portal primero.

⏱️

Inactividad sincronizada entre los 4 — mismas funciones SQL, mismo JS

Verificado con búsqueda directa: Portal, TH, Bienes y Bitácoras llaman a las mismas dos funciones cross-DB (PORTAL_APM.dbo.fn_InactividadSegundos / fn_InactividadAvisoSegundos) y cargan el mismo js/inactivity-warning.js (§8b) — no es "cada módulo con su propio timer", es una sola configuración real.

Config
/admin/inactividad — override por usuario, por módulo, o global
→
Cascada SQL
fn_InactividadSegundos(id_usuario, módulo) — usuario > módulo > global
→
Cada app
cachea el resultado 5 min en SU sesión, propia o compartida

En TH, la cascada se resuelve pasando su propio _portal_user_id_link (el id de portal vinculado, 0 si la cuenta es TH-only) y el código de módulo fijo 'TALENTO_HUMANO' — así un override configurado específicamente para esa persona aplica igual, entre por donde entre. El resultado se cachea 5 minutos en $_SESSION para no golpear la base en cada request; invalidarCacheInactividad() existe para el caso real de que un admin cambie la config y quiera que aplique sin esperar esos 5 minutos ni cerrar sesión.

Consecuencia práctica: si el administrador sube el timeout global a 60 minutos desde /admin/inactividad, una persona navegando entre TH y Bienes en la misma sesión de trabajo ve el mismo comportamiento en ambas — no hay que configurarlo por separado en cada módulo.
🔐

MFA al cambiar de módulo — el gateway /ir

ModuleGateController.php

El puente de sesión (arriba) resuelve identidad, pero un usuario con MFA activo en el portal no debería poder saltar a un módulo integrado esquivando el segundo factor. Los links del sidebar hacia apps/* no apuntan directo — pasan por /ir?destino=..., un único punto que decide si hace falta reconfirmar.

No es en cada click: usa una ventana de frescura (CORE_Config.MFA_FRESCURA_SEGUNDOS, 20 minutos por defecto). Si $_SESSION['_mfa_verificado_en'] es más reciente que esa ventana, pasa directo; si no, pide el código TOTP de nuevo (misma pantalla, sin repetir usuario/clave) antes de continuar al destino. destinoSeguro() valida que el destino empiece con apps/ y no contenga :// — nunca redirige a una URL externa arbitraria.

Detalle completo de identidad, código-a-código: §6b libs/SsoClient.php (para módulos que SÍ requieren el mecanismo de token) y GUIA_SSO_LOGIN_ENTRE_MODULOS.md (los 5 sp_SSO_*, cómo dar de alta una app nueva, manejo de errores). Esta sección cubre el camino real que usan HOY los 3 módulos embebidos — que no es ese mecanismo.

§11 MfaHelper — TOTP nativo del portal

core/MfaHelper.php, 161 líneas.

Mismo algoritmo RFC 6238 que ya usa apps/talento_humano/core/Auth.php — no se reinventó la matemática, se replicó el patrón validado en producción. La clave de cifrado del secreto TOTP vive en CORE_Config (mismo mecanismo que SSO_SECRET/PASSWORD_PEPPER). Caller real: ModuleGateController.php y Credenciales/AuthController.php.

  • generateSecret(): 20 bytes random en base32.
  • encryptSecret()/decryptSecret(): AES-256-GCM, IV de 12 bytes + tag de 16 + AAD fijo — el secreto TOTP nunca en claro.
  • verify($secret, $code, $lastStep, &$matchedStep): ventana ±1 paso de 30s con anti-replay real — un $lastStep ya usado nunca vuelve a aceptarse.

§12 Gotchas reales — si vas a tocar este código

8 casos reales documentados, no hipotéticos.

⚠️

sqlsrv_configure("WarningsReturnAsErrors", 0) tiene que ejecutarse ANTES de cualquier conexión — si se agrega una conexión sqlsrv nueva sin este flag, un SP con PRINT puede reportarse como fallido sin haberlo hecho.

⚠️

Database::getInstance() es singleton por PROCESO PHP, no por request — bajo php -S (proceso persistente) puede importar si cambian credenciales en caliente; en Apache/mod_php cada request es proceso/hilo nuevo, no es problema real ahí.

⚠️

lastInsertId() vía SCOPE_IDENTITY() en query separada puede devolver NULL si el driver sqlsrv no mantiene el mismo scope — usar OUTPUT INSERTED.id en el INSERT mismo cuando el ID importa de verdad.

⚠️

El mapa de módulos de ModuleSecurity::checkAccess() está duplicado respecto a CORE_Modulos/CatalogoModulos — pero como ese método está muerto (§6), en la práctica no hay dos lugares que mantener sincronizados hoy; si se revive, revisar esto primero.

⚠️

SyncPermisosModulo/SsoClient abren conexiones sqlsrv nuevas cada vez que corren, no reutilizan Database::getInstance() (apuntan a BD distinta) — costo irrelevante hoy, a tener en cuenta si se llaman en loop.

⚠️

Nada en core/libs/ valida que CORE_Config exista antes de leer SSO_SECRET/MFA_ENCRYPTION_KEY/PASSWORD_PEPPER — si la tabla no existe (instalación nueva sin script de esquema completo), estos métodos fallan con excepción SQL, no un mensaje claro.

⚠️

web.config reescribe con ?url=... pero index.php nunca lee $_GET['url'] (§1a) — no confiar en ese parámetro si algún día se toca soporte IIS.

⚠️

libs/XlsxWriter.php (portal) y apps/talento_humano/core/XlsxWriter.php son implementaciones DISTINTAS — no asumir que un fix en una aplica a la otra.
