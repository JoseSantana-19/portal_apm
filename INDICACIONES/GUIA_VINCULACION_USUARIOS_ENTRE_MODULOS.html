Cómo se conectan los usuarios entre todos los módulos

Explicado sin tecnicismos: qué problema resuelve, cómo funciona hoy, y cómo va a funcionar cuando se conecte el Portal de Trámites en Línea (y cualquier módulo futuro).

La idea completa, en una frase Cada persona tiene UNA sola cédula (o RUC). Ese número nunca cambia y es el mismo en todos los sistemas — por eso es lo que se usa para saber que "el usuario 47 de un sistema" y "el usuario 900 de otro sistema" son la MISMA persona.

1 El problema, explicado fácil

Imaginate que trabajás en un edificio con varias oficinas: Talento Humano, Control de Bienes, Bitácoras... y ahora se suma una más: Trámites en Línea, donde la gente hace papeleos por internet.

Cada oficina tiene su propia lista de gente, con su propio número de fila. En la lista de Trámites en Línea vos sos "el número 900". En la lista de Talento Humano sos "el número 47". Son números completamente distintos, de sistemas que nunca se hablaron entre sí.

Analogía
Es como si en el gimnasio fueras el "socio 900" y en la biblioteca fueras el "socio 47" — ningún número tiene que ver con el otro. Pero vos seguís siendo LA MISMA persona en los dos lados, y lo que nunca cambia es tu cédula.

El problema real: queremos que si sos empleado interno Y ADEMÁS usás Trámites en Línea, puedas entrar una sola vez y moverte entre todo sin que te pidan usuario y clave de nuevo en cada oficina — pero sin tocar ni romper nada de lo que ya funciona para la gente que SOLO usa Trámites en Línea (la gran mayoría, gente del público en general que nunca necesita entrar a los módulos internos).

2 La cédula (o el RUC) es la llave

Todo este sistema ya tiene una regla de oro, aplicada desde el día uno en el Portal APM: nadie se identifica por un número de sistema — todos se identifican por su cédula (10 dígitos, personas) o su RUC (13 dígitos, empresas). Ese número es el único dato que de verdad "sigue siendo el mismo" sin importar en cuántos sistemas distintos exista esa persona.

🪪 Cédula / RUC

El número real de la persona en el Registro Civil o el SRI. Nunca cambia, nunca se repite entre dos personas distintas. Es el ÚNICO dato confiable para decir "estos dos registros son la misma persona".

🔢 ID interno de cada sistema

El número de fila que le asigna CADA base de datos por separado (empleado_id en Talento Humano, id_usuario en el portal, un ID propio en Trámites en Línea). Cambia de sistema a sistema — nunca se usa para reconocer a una persona entre dos sistemas distintos.

Por eso, cuando este documento habla de "vincular usuarios", nunca significa "hacer que los números de ID coincidan" — significa "confirmar que la cédula/RUC de un lado es la misma que la del otro lado".

3 Cómo funciona HOY (Talento Humano, Bienes, Bitácoras)

Esto ya está construido y probado — no es una promesa, funciona ahora mismo.

Ya funciona hoy

Estos 3 módulos viven en el MISMO servidor que el portal, así que pueden "compartir la sesión" — cuando iniciás sesión una vez en el portal, cada uno de los 3 revisa automáticamente "¿esta persona ya inició sesión en el portal? Si sí, dejala entrar sin pedirle nada de nuevo."

1

Iniciás sesión UNA vez

Con tu cédula y clave, en el portal principal.

2

Vas a Talento Humano / Bienes / Bitácoras

Cada uno revisa si ya iniciaste sesión en el portal.

3

Entrás directo, sin pedirte nada de nuevo

Con tu rol y permisos reales de ese módulo, ya resueltos automáticamente.

Este método (compartir la sesión directamente) solo funciona porque los 3 viven en el mismo servidor. Trámites en Línea va a vivir en OTRO servidor — por eso necesita un método distinto, que es el de la sección 4.

4 El mecanismo real para sistemas en OTRO servidor (SSO)

Esto también ya existe y está probado — 5 procedimientos en la base de datos PORTAL_APM que cualquier sistema externo puede usar para confirmar identidad sin necesidad de compartir el servidor.

Ya funciona hoy — probado de punta a punta
Analogía
Pensalo como el sistema de "iniciar sesión con Google" que ves en muchas páginas. La página no guarda tu clave de Google — le pregunta a Google "¿esta persona es quien dice ser?", Google responde sí o no, y le entrega un pasecito (token) que esa página usa después para saber que sos vos, sin volver a pedirte la clave en cada click. Acá pasa exactamente lo mismo, pero el "Google" es PORTAL_APM.

El "pasecito" en este sistema se llama token: un código larguísimo, imposible de adivinar, que expira solo después de varias horas. 5 procedimientos (funciones guardadas dentro de la base de datos) manejan todo el proceso:

1

sp_SSO_Login — "¿esta cédula existe y está activa?"

El sistema externo manda la cédula y su propia credencial de aplicación (para que PORTAL_APM sepa que quien pregunta es un sistema autorizado, no cualquiera). Si la cuenta existe y está activa, responde "OK" — si no, dice por qué (no existe, está bloqueada, está inactiva).

2

El sistema externo revisa la clave

La clave nunca se compara dentro de la base de datos — el sistema externo recibe la clave encriptada guardada y hace la comparación él mismo. Así, PORTAL_APM nunca "ve" contraseñas de otros sistemas.

3

sp_SSO_ConfirmarLogin — entrega el pasecito

Si la clave coincidió, este procedimiento genera el token (el "pasecito") y le dice cuánto tiempo dura antes de vencer.

4

sp_SSO_ValidarToken — revisa el pasecito en cada visita

Cada vez que la persona hace algo nuevo, el sistema externo muestra el token en vez de pedir la clave otra vez. Este procedimiento confirma que sigue siendo válido y no venció.

5

sp_SSO_Logout / sp_SSO_RegistrarFallo

Al cerrar sesión, se anula el pasecito. Si la clave fue incorrecta, se cuenta como intento fallido — con el mismo bloqueo automático que ya usa el login normal del portal (3 intentos fallidos bloquean la cuenta un rato).

Todo esto ya se probó real, de principio a fin, con una cuenta de prueba — funciona, incluyendo el caso de clave correcta, clave incorrecta, credencial de aplicación inválida, y token vencido. Detalle técnico completo (para quien programe la conexión) en GUIA_SSO_LOGIN_ENTRE_MODULOS.md, en esta misma carpeta.

5 Trámites en Línea — cómo se conectaría (futuro)

Nada de esta sección existe todavía — Trámites en Línea hoy no está conectado con nada. Es la propuesta de cómo hacerlo cuando llegue el momento, sin inventar mecanismos nuevos: reutilizando el SSO de la sección 4.

Propuesta a futuro — no implementado aún

Dato clave que cambia todo el diseño: Trámites en Línea corre en OTRO servidor de base de datos, separado del que tiene PORTAL_APM. Por eso NO puede usar el método "compartir sesión" de la sección 3 (ese solo funciona en el mismo servidor) — tiene que usar el mecanismo de tokens de la sección 4, exactamente como cualquier sistema externo.

No todos los usuarios de Trámites necesitan esto

Esto es lo más importante de toda la propuesta: la gran mayoría de la gente que usa Trámites en Línea son ciudadanos comunes — hacen un papeleo y listo, nunca van a necesitar entrar a Talento Humano ni a ningún módulo interno. Para ellos, nada cambia, nada se toca, siguen usando Trámites en Línea exactamente igual que ahora.

El puente solo importa para el ~25% que además es personal interno (o va a necesitar serlo con los módulos nuevos). Y ese puente no se activa nunca a la fuerza — solo se dispara el día que esa persona específica intenta usar algo del lado del CORE.

Tipo de usuario de Trámites¿Necesita vinculación?Qué pasa
Ciudadano común (~75%)NoSigue usando Trámites en Línea exactamente igual que hoy. Cero cambios.
Personal interno / futuros módulos (~25%)SíLa primera vez que intenta entrar a algo del CORE, el sistema busca su cédula y arma el puente automáticamente.

La pieza que falta hoy: una libreta de apuntes del vínculo

El mecanismo de tokens (sección 4) confirma identidad, pero no "recuerda" a quién ya vinculó. Para no repetir la búsqueda por cédula cada vez y para poder corregir un caso puntual a mano (una cédula mal escrita, por ejemplo), se propone una tabla nueva, chiquita, que funciona como una libreta de apuntes:

SQL — Propuesta, tabla nueva en PORTAL_APM
CREATE TABLE dbo.CORE_Vinculos_Externos (
    id_vinculo          INT IDENTITY(1,1) PRIMARY KEY,
    sistema_origen      VARCHAR(50)  NOT NULL,  -- ej. 'TRAMITES_ONLINE'
    id_usuario_externo  VARCHAR(50)  NOT NULL,  -- el numero de fila EN Tramites
    identificacion      VARCHAR(13)  NOT NULL,  -- cedula (10) o RUC (13)
    id_usuario_core     INT          NULL,      -- a que cuenta de CORE_Usuarios corresponde
    metodo_vinculo      VARCHAR(20)  NOT NULL,  -- 'AUTOMATICO' o 'MANUAL'
    fecha_vinculo       DATETIME     NOT NULL DEFAULT GETDATE(),
    CONSTRAINT UQ_vinculo UNIQUE (sistema_origen, id_usuario_externo)
);

Es literalmente una lista de "el usuario 900 de Trámites es la cédula 1234567890, que corresponde al usuario 47 de CORE" — una fila por cada persona que de verdad usa los dos sistemas. El 75% que solo usa Trámites nunca aparece acá.

Cómo sería el primer ingreso de alguien del 25%

1

La persona ya usa Trámites en Línea normalmente

Con su cuenta de siempre, sin ningún cambio.

2

Un día necesita entrar a un módulo interno

Por ejemplo, ahora también es empleado y necesita ver su información en Talento Humano.

3

El sistema busca su cédula en la "libreta"

Si no hay vínculo todavía, busca esa misma cédula en CORE_Usuarios (el directorio central del portal).

4

Si la encuentra, usa el SSO de la sección 4

Confirma identidad con el mecanismo de tokens y anota el vínculo en la libreta — la próxima vez ya no hace falta repetir la búsqueda.

5

Si NO la encuentra, no se le da acceso solo

Las cuentas del CORE se crean únicamente desde Talento Humano (regla ya establecida del proyecto) — si la persona todavía no tiene expediente ahí, alguien de Talento Humano la registra primero, y recién ahí el puente puede encontrarla.

Por qué es seguro este diseño
Nadie puede "auto-otorgarse" acceso a un módulo interno solo por tener cuenta en Trámites en Línea. El puente solo conecta cédulas que YA tienen una cuenta real y aprobada del lado del CORE (creada por Talento Humano) — nunca crea una cuenta nueva por su cuenta.

6 Receta para conectar CUALQUIER módulo nuevo, a futuro

Esta es la pregunta que hay que hacerse primero, y después seguir la receta que corresponda — ya probada 4 veces en este proyecto (Talento Humano, Bienes, Bitácoras, y la propuesta de Trámites):

¿Va a vivir en el MISMO servidor que el portal?

Sí → usar el método de sesión compartida (sección 3). Es el más simple, no hace falta credencial de aplicación ni tokens.

¿Va a vivir en OTRO servidor, u otra tecnología?

Sí → usar el método de SSO por token (sección 4). Registrar el módulo nuevo una sola vez con sp_SSO_RegistrarApp, y ya puede validar identidad contra CORE_Usuarios sin acceso directo a la base.

En los dos casos, la regla de fondo nunca cambia: la cédula (o RUC) es lo único que identifica a una persona entre sistemas distintos. Ningún módulo nuevo debería inventar su propio esquema de identidad desde cero.

7 Glosario — términos sin jerga

COREEl "cerebro" compartido del portal: login, sesión, permisos, menú. Todos los módulos se apoyan en él.
CORE_UsuariosLa tabla que es el directorio central de personas — una fila por cada cuenta real del sistema.
Cédula / RUCEl número real de identidad de una persona (10 dígitos) o empresa (13 dígitos). Nunca cambia, nunca se repite.
ID internoEl número de fila que cada base de datos asigna por su cuenta. Distinto en cada sistema, nunca sirve para reconocer a alguien entre dos sistemas.
SesiónEl "recordatorio" de que ya iniciaste sesión, mientras navegás sin que te pidan la clave en cada página.
TokenUn código larguísimo e imposible de adivinar que funciona como pasecito temporal de acceso, para sistemas que no comparten sesión.
SSO"Single Sign-On" — iniciar sesión una sola vez y quedar identificado en varios sistemas, sin repetir usuario/clave.
Cross-DBCuando una base de datos consulta directamente otra base de datos distinta (solo funciona si están en el mismo servidor).
Procedimiento almacenado (SP)Una "receta" guardada dentro de la base de datos que hace una tarea específica cuando se la invoca — acá, cada paso del login SSO es uno de estos.
VinculaciónConfirmar y anotar que un usuario de un sistema es la misma persona que un usuario de otro sistema, usando la cédula como prueba.
